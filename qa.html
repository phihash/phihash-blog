Docker

コンテナの正体は、ホストから見ると何？

分離されたプロセス。ホストとは同じカーネルを共有している。

Docker はコンテナの起動時に何を作る？

namespace と cgroup。namespace は見える範囲を分け、cgroup は使える量を制限する。

namespace は何を分ける？

PID、ネットワーク、ホスト名など。だからコンテナからホストのプロセスは見えない。

コンテナの中で最初のプロセスの PID が 1 なのはなぜ？

PID は namespace ごとに 1 から数えるから。同じプロセスが、Linux ホストの ps では別の番号で見える。Mac の Docker Desktop は Linux の VM の中でコンテナを動かすので、Mac の ps には出ない。

cgroup は何を決める？

プロセスのまとまりごとの、メモリや CPU の上限。

イメージとは何？

イメージレイヤー（読み取り専用）を重ねたもの。

コンテナをつくると、イメージの上に何が加わる？

コンテナレイヤー（書き込み可能）。同じイメージから作ったコンテナはイメージレイヤー（読み取り専用）を共有し、コンテナごとに別なのはコンテナレイヤー（書き込み可能）だけ。

コンテナの中でイメージのファイルを書き換えると、どうなる？

そのファイルをコンテナレイヤー（書き込み可能）にコピーしてから変更する（コピーオンライト）。イメージ自体は変わらない。

docker stop で止めると、書き込んだデータはどうなる？

コンテナレイヤー（書き込み可能）ごと残る。docker start で再開すれば、そのまま使える。

docker rm で削除すると、書き込んだデータはどうなる？

コンテナレイヤー（書き込み可能）ごと消える。残したいデータは、レイヤーの外にあるボリュームに置く。

ボリュームとは何？

Docker が管理する、ホスト上の保存場所。コンテナを削除しても残り、新しいコンテナでもそのまま使える。

ボリュームを消すには？

docker volume rm。docker rm でコンテナを消しても、名前付きボリュームは消えない。

コンテナのメモリ上限を見張っている仕組みは？

cgroup。プロセスのまとまりごとにリソースを制限する Linux カーネルの仕組み。

コンテナがメモリ上限を超えると何が起きる？

カーネルの OOM キラーが、cgroup 内でメモリを多く使うプロセスを選んで SIGKILL (9) を送る。

終了コード 137 の意味は？

128 + 9 で、SIGKILL で終了したということ。OOM とは限らず、docker kill でも 137 になる。

137 が OOM かどうかの確かめ方は？

docker inspect -f '{{.State.OOMKilled}}' コンテナ名 が true か見る。

アウトオブメモリとメモリリークは同じ？

違う。リークは OOM の原因の一つ。巨大なデータの読み込みや、上限設定が小さい場合も、リークなしで OOM になる。
