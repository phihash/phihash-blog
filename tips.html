1on1

「最近どう？」ではなく、事実 → 感情 → 将来の順に聞く。

  1. 事実：何が起きたか（観察できる事実）
    • NG: 最近どう？
    • OK: 今週やった作業の中で、一番時間を溶かしたのは何？
    • OK: 直近のタスクで、想定より時間がかかったところはどこ？
  2. 感情：それについてどう感じたか（事実に紐づけて）
    • OK: そのタスク、進めてるときどんな気持ちだった？
    • OK: それをやってて、楽しかった部分としんどかった部分ってどこ？
  3. 将来：このまま続けたいと思えるか（踏み込んで聞く）
    • OK: 3か月後、今のチームでどんな仕事をしていたい？
    • OK: 今の仕事の進め方を1つだけ変えられるなら何を変える？
    • OK: このチームに1年後もいると想像したとき、しっくりくる？

設計とアーキテクチャ

設計は「どう作るか」を決めること、アーキテクチャは「何を優先するか」を決めること。

  • コードの書き方やクラス構成を決めるのと、システム全体としてスケーラビリティを取るか開発しやすさを取るか、みたいな話は、たしかにレイヤーが違った。
  • 決めたことが現場にちゃんと伝わらなかったり、逆に現場での気付きがアーキテクト側にフィードバックされなかったりして、結局アーキテクチャが形だけのものになってしまう。アーキテクチャは、アーキテクトと開発チームが常にやり取りしながら一緒に育てていくもの。
  • メリットだけ語れる人は多いけど、デメリットまでちゃんと説明できる。
  • ひとつの技術のスペシャリストであるより、「この問題には解決策が5つくらいある」と知っている方が価値が高い。

アドバイス

「自分はできた」を根拠に、人に努力を求めない。向き不向きがある。

  • よかれと思ってアドバイスするが、ただ教訓を語ったり、説教するだけの場合が多い。だいたいは、ふがいないと怒ったり、強く注意する。
  • 根拠は「自分はちゃんとやってきた」ということ。自分ができたんだから、あなたもしなさい。それができないのは、あなたの努力が足らないから。
  • 「努力していい大学に行く」「立派な会社に勤める」「仕事で結果を出す」という価値観で生きてきて、その価値観から見た「努力してない人」「ふがいない人」にアドバイスしたくてたまらなくなる。
  • 人間には向き、不向きがある。「ふがいない」「もっと努力しろ」は、本人が自分を責めることはあっても、他人が口にする言葉ではない。

  • テレビのリモコンは冪等でない。

HOMEタブ

iOS アプリのナビゲーションは、ユーザーがコンテンツや体験に集中できるよう、意識させないほど自然であるべき。タブの名前は「Listen Now」「Radio」のように簡潔かつ説明的にし、タブを見ただけで役割が分かるのが理想。

Apple の公式の見解では、「HOMEタブ」のようなものは推奨されていない。

  1. HOMEタブは、アプリの情報階層を混乱させる可能性がある。
  2. ほかのタブやアプリ内の領域の機能が、十分な文脈なしに1つの画面に複製されると、冗長さや混乱を生む。
  3. 結果としてHOMEタブはすべての機能の奪い合いの場になり、発見しやすくするつもりが、かえってコンテンツの理解と行動の乖離を生む。
  4. 機能が重複していると、意図しないタブジャンプ（別のタブへ自動で移動すること）が起きやすく、ユーザーは不快で方向感覚を失う。

App Store アプリの「Today」も、いろいろな機能を集めたタブではなく、今日のおすすめや注目のコンテンツなど、最新情報を届けるタブになっている。違いは「どういう名前で呼ぶか」というラベリングの部分も多い。Apple も避けたいとは言いつつ、HOME という便利なラベルを使わざるを得ないときはあるんだと思う。

HOMEタブを置くなら：

  • 役割が明確：なんでも置き場ではなく、「今日のあなたに最適化されたコンテンツ」を出す場など、目的が決まっている。
  • 階層上の位置づけを説明できる：ほかのタブとの関係が明確で、機能が重複しない。
  • ユーザーの次の一歩が見える：見て終わりではなく、詳細・検索・カテゴリなど別のタブへ自然に誘導できる。
  • 名前に甘えない：HOMEだから何でもいいではなく、名前以上に UI の構造で役割を示す。

「HOMEだから全部入れておこう」という発想は、Apple が警鐘を鳴らすとおり混乱のもとになりやすい。

UI とは

  • UI は User Interface。User と System との Interface（境界、接点）。User が System に働きかけるとき、System が User に干渉するときの、やり取りの接点が UI。
  • 「UI を設計する」は「User と System の境界をデザインする」こと。ユーザーは、デザインされたインターフェースを通して、システムを見たり、聞いたり、触ったりする。
  • 真に優れたインターフェースは、見た目がいい感じなものではなく、視覚・聴覚・触覚など、ユーザーがシステムに対してできるすべての知覚がより良く設計されているもの。見た目だけがいいのは「ビジュアルデザインがいい」というだけで、インターフェースとして良いとは限らない。

見えづらさのある人に聞いたこと

  • 「削除」「追加」のような関連する操作ボタンは、バラバラに置くより隣り合わせに置くのがよい。ただ、離れていると誤操作は減るかも、という意見もあった。近づけるだけでなく、押し間違えないための十分な余白も欠かせない。
  • 「色」だけで区別するより、見出しや余白を組み合わせると迷いにくく、見えづらさのある人にも伝わりやすい。
  • 「黒背景に白文字のほうが見やすい」「ゴシック体より明朝体のほうが見やすい」という声もあった。一般には「ゴシック体や UD フォントが見やすい」と言われるが、見やすさには大きな個人差があり、世間的に良いとされるデザインがすべての人に当てはまるわけではない。
  • だから、ユーザー自身が見やすい背景色やフォントを選べる仕組みが大事。

良い UI の条件

  • 安易な UI の変更が一番 UX に悪い。ユーザーは慣れで動いている。
  • 欲しい機能の順に UI が大きい。
  • メイン機能のそばにサブ機能を置く。
  • 操作の選択肢が少ない。
  • 文字が少ない。

いい UI は、サービスの機能をユーザーのいい体験に変えられる。

  • アイコン付きにすると、アクションがイメージしやすくなる。
  • 必要なアクションは、必要なタイミングで伝える。
  • アクションは時系列で右に向かうようにする。
  • 良質な UI 設計の三大原則：
    • 発見できる：ユーザーがひと目で何をすればいいかわかる。
    • 予測できる：押す前に何が起きるか想像できる。
    • 学習できる：1度使えば、次から説明なしでも使える。
  • 良い UI は「そのサービスらしいか」「ユーザーに良い変化が起きるか」も担う。

フォームまわりの細かい配慮

  • 規約やガイドラインなどはリンク付きにする。
  • 銀行振込の口座番号など、入力ミスが起きそうな値はコピーできるようにする。
  • 送信中はボタンを disabled にする（二重送信の防止）。

日付選択 UI の使い分け

  • カレンダー UI は単一の日付選択には向いていない。素直にドラムロール UI を使ったほうがいい。
  • カレンダー UI が向くのは、範囲選択や開始/終了の選択。

カラーユニバーサルデザイン

  • 色覚は人によって違う。特定の配色だと「同じ色に見えて区別できない」人がいる。
  • 色が変えられない・伝わらないなら、色以外の情報を足す。色味を変換するだけでも配慮になる。グレースケールにしても区別がつくかを見る。
  • ディザ処理（ハッチング）は、違う色だと分かるように模様をつける手法。『いらすとや』のイラストは、髪などの濃い色の部分にシマシマや模様が入っていて、まさにこれ。
  • 色で区別させる UI は、模様や形も併用すると親切かもしれない。

日本語の組版

note の OGP 画像の自動生成で、文字をきれいに組むためにやっている工夫。

  • 文字の「幅」で考える：日本語は文字種で見た目の幅がぜんぜん違う（全角の漢字、半角の英数字、句読点）。だから「何文字か」ではなく、文字種ごとに重みをつけた「幅の合計」で、収まるかを判定する。
  • サイズは潔く諦めながら決める：短い文は大きく、長い文は小さく。フォントサイズを何段階か用意し、大きいほうから「組んでみて、見切れたり行のバランスが崩れたら一段下げる」。合格した時点で確定して、それ以上は探さない。延々と最適解を探させると保守が破綻する。
  • 改行は AI の判断を「直してあげる」：日本語の改行位置は、Google の分かち書きエンジン BudouX に任せる。
  • 一文字だけ行に取り残さない：組版用語で「孤立行」「寡婦行」。先頭行や末尾行に文字が1〜2個だけ残ると見栄えが悪いので、検知して前後の行との結合を試みる。
  • 省略の「…」にもこだわる：「noteを…」のように助詞だけ残ると雑に切られた印象になる。助詞の前が漢字や英数字なら助詞ごと削り、かなで終わるなら助詞を残す。
  • 文字を「詰める」：「デザイン」とカタカナで打つと、「ザ」と「イ」のあいだが妙に空いて見える。そういう特定の文字ペアごとに、ほんのわずかに詰める。

日報
  • 日報は「業務報告」ではない。やったことの報告も必要かもしれないが、ひとりひとりが「今何をやっているか」を「共有」するためにやる。
  • 日報は「義務」ではない。義務になったら楽しんで書けない。「ひとこと」が思い浮かばないときは、無理して書かなくていい。
  • 日報は「書く」だけでなく、ほかのメンバーの日報を「読み、突っ込む」ことで学びが生まれる。

書く項目は3つだけ。

  • やった
  • やる
  • ひとこと

簡単にすること、続くようにすること、負担にならないこと。そして、とにかくみんなが書きたくなるようにすること。一番怖いのは「形骸化」。

仮説思考

「理由はいいからさっさと腕を磨け」

  • 優秀なクリエイターは、必ずしも細かくインプットを求めない。情報がないならないで、自分で調べたり仮説を立てたりして、ある程度作ってしまえる。
  • そもそも、依頼者の頭の中に明確な答えがないことも多い。そんなときはクリエイターが仮説で穴を埋め、作ったものを見せて意見をもらう。この方が早い。この場合、インプットは最低限でいい。
  • どれだけ情報をインプットしても、十分になることはない。ある時点から、情報量が多いことのデメリットがメリットを上回る。一定以上の情報は、結局捨てることになる。
  • 戦略や方向性をやたらインプットしたがる人は、仮説思考力が弱いのも一つの原因かもしれない。

つくる前の問い

「なぜ・何を・誰のためにつくるか」に自分なりの答えを持てるか。

  • このサービスや機能は、誰にとってどんな価値を持つか。
  • 使い始める理由と、使い続ける理由が用意されているか。
  • 会社と社会の両方に利益をもたらし、それが循環するか。

「伝わり方」の設計が要る。条件は、価値が瞬間的に分かること、自分が恩恵を受ける当事者だと思えること、ほかで代替できないと分かることの3つ。

KPI と Evals

KPI は「速いか、安いか、たくさんさばけているか」を測る。Evals は「中身が自社にとっての良い仕事の定義に合っているか」を測る。この2つは別々に持つしかない。

なぜ KPI だけでは足りなくなったか

  • これまで多くの組織は、KPI さえ追っていれば品質も維持できると信じていた。その信頼が成り立ったのは、人間が処理していたから。
  • KPI ハック自体は昔からあった。架電件数を追うと形だけの短いコールが増え、対応件数を追うとテンプレ回答で「処理済み」にする運用が広がり、ストーリーポイントを追うと小さいチケットばかり切られる。
  • ただ人間には、同僚の目、顧客の反応、上司のレビュー、プライド、罪悪感、評判への懸念という「第二の評価系」が暗黙のうちに働いていて、中身を壊す行動にブレーキがかかっていた。
  • AI にはそれがない。「件数を増やせ」と言われれば、件数だけ伸びて中身が崩れても気にしない。もともとあった KPI ハックの可能性が、AI の規模と速度で表に出てくる。
  • AI で問題になる KPI 設計は、もともと脆弱な KPI 設計だったのかもしれない。人間の「他者の目を気にする」機構が、それを覆い隠していただけ。
  • 「品質 KPI を足せばいい」はたいていうまくいかない。品質は1つの数字に圧縮しにくく、数字の取り方が論点になって元の問題に戻る。

Evals を作ろうとすると突きつけられること

  • 自社が「良い仕事」と呼んでいるものを、誰も定義していなかった。ベテランの判断は機能していたが、それはその人の中にしかない、明文化されていない暗黙知だった。
  • その人が抜けたら誰も再現できず、新人にも教えられず、外向きに「我々の品質はこういうもの」と説明することもできない。
  • Evals 設計で本当に難しいのは、AI の精度評価ではなく、自社の自己理解の解像度。
  • Evals を真面目に作ろうとすると、業務の棚卸し、期待値の言語化、ベテラン同士の合意形成、例外処理の明文化、線引きの定義に向かう。皮肉なことに、AI を入れようとして初めて、本来やるべきだった業務の言語化が進む。
  • それが進んでいない組織に AI を入れても Evals が作れず、品質が崩れたり、属人化したまま運用されたりする。DX でよくある失敗パターン。
  • Evals は一度作って終わりではなく、自社の「良い仕事の定義」を更新し続ける営み。

突き詰めれば、「自社が何を良いと考えているかを、組織として答えられますか」という話。なお「Evals（evaluations）」はもともと機械学習の分野の用語。

店舗とクラウドをつなぐ予約機能

システムが正しく動くことと、お客さまの体験が成立することはイコールではない。

  • 電話を避けるユーザーは予約を使わず、結果として店頭で待たせたり断ったりしていた。だから予約機能を作る。
  • 「あの部屋が今空いているか」は、各店舗のローカル POS（店内の PC）の中にしかない。既存の POS には手を入れず、部屋の空き状況だけをクラウドに吸い上げる方針にした。
  • 店舗のネットワークは安定しているとは限らない。通信が途切れる中で、部屋の状態をリアルタイムに近い精度でクラウドに反映し続ける必要がある。
  • 電話予約や店頭のウォークイン受付との競合もある。部屋を確保するときに POS と連携してロックをかけ、ダブルブッキングを防ぐ。地味だが非常に重要。
  • 料金体系はとにかく複雑で、計算ロジックも各店舗の POS の中でしか動いていなかった。それをクラウドに作り直し、POS の計算結果と突き合わせて検証するのが一番骨が折れた。「この店舗のこの曜日のこの時間帯にこの会員種別で入ると金額が合わない」を1件ずつ潰す。
  • 予約より10分早く来た人の入室時刻をどう扱うか。遅刻したらどこまで予約を保持するか（一定時間を超えたらウォークイン扱いにする、など）。実際の店舗で何が起きるかを想定して、ひとつずつ潰していく。

チームの目標設定（アウトプットとアウトカム）

「アウトプット志向は良くない」は雑すぎる一般化。目標は、チームが自分の手で動かせるか、インパクトへの因果が短くつながっているか、の2つで選ぶ。

うまくいかなかった目標

  • 「〜の機能を、いつまでに出す」：分かりやすいが、出すこと自体がゴールになり「なんのために作っているんだっけ？」が抜け落ちる。交渉の余地が少なく、「言われたものを作るだけ」の空気になりがち。
  • 「ユーザーの利用率を X% 改善する」：ビジネスの KPI はチームの手が届くところから遠すぎる。達成しても未達でも、開発チームの要因か営業やマーケの要因か切り分けられず、ふりかえりが毎回ふわっとする。

3つの言葉の整理（『Outcomes Over Output』）

  • インパクト：組織として得たいビジネス上の利益。（例: 売上の増大、コストの削減）
  • アウトカム：インパクトを出すために起こしたい、ユーザー行動の変化。（例: ユーザーがメールを開くようになる）
  • アウトプット：アウトカムを起こすために作る、プロダクトの変化。（例: 開きたくなるメール通知）

「アウトカム＝ユーザー行動の変化」が良い言語化。「価値を届けられたか」は解釈が割れるが、「ユーザーがこう動くようになったか」なら観測すればはっきりする。ただし、ビジネスの利益につながる行動の変化だけがアウトカム。

2つの基準で見直すと

  • 「機能をいつまでに出す」は、手で動かせるが、インパクトにどうつながるかを説明できない。
  • 「利用率を X% 改善」は、因果の先端だけを掴んでいて、チームの手で動かせない。
  • ユーザー行動の変化は、その因果のちょうど真ん中にある観察できる中継点。これを目標の中心に置くと、2つの基準を満たしやすい。

例

  • 手応えのあった「プレスリリースを n 本出す」：インパクトは商談を増やすこと。アウトカムは、プレスリリースを見て興味を持つ人が増える、インサイドセールスがそれをきっかけにコール対象を増やす、営業が商談でその話をすること。アウトプットは、プレスリリースを出す、好評そうな機能を作ること。
  • 新基盤：インパクトは SaaS×マッチングという新しいビジネスモデルの立ち上げ。アウトカムは、エンジニアが開発の重複を避けて新しいプラットフォームの上で仕事をするようになること。アウトプットは、共通でデータを扱える新しい基盤を提供すること。

UXライティング

音声で聞いている人も含めて、だれでも読みやすい文章にするための書き方。

文章

  • タイトルは、記事の内容が伝わる言葉を前に持ってくる。
    • △ 【重要】お知らせ
    • ◎ 秋の写真展を10月3日から開催します
  • 見出しは、それだけで内容がわかるようにする。
    • △ はじめに／その1／まとめ
    • ◎ 応募に必要な3つの書類
  • 見出しは、大きい階層から順番に使う。文字を大きくしたいだけで見出しを使わない。強調したいだけなら太字。
  • 箇条書きは、行頭に「・」を打たず、エディタの箇条書き機能を使う。機能で作ったリストは「ここから3個の項目が始まる」という情報を持つが、記号を打っただけの行はふつうの文章として扱われる。
  • 1文を長くしすぎない。音声で聞いている人は、気になったところへ戻るのがかんたんではない。1文の読点が3つを超えたら、分けることを考える。
    • △ 応募は10月3日までで、書類は3種類必要ですが、うち1つは郵送のみの受付となっているため、早めにご準備ください。
    • ◎ 応募は10月3日までです。書類は3種類必要で、このうち1つは郵送でのみ受け付けます。早めに準備してください。
  • 色だけで情報を伝えない。
    • △ 赤い文字の項目は必須です
    • ◎ 「必須」と書いてある項目は、かならず記入してください
  • 位置だけで情報を伝えない。
    • △ くわしくは下の画像を見てください
    • ◎ 応募に必要な書類は、身分証明書・住民票・申込書の3つです
  • 記号の使い方に気をつける。「13時-15時」ではなく「13時から15時」、「7/28（火）」ではなく「7月28日（火曜日）」。
  • テキストリンクの文字は、リンク先がわかるように具体的に書く。
    • △ くわしくはこちら
    • ◎ 秋の写真展の応募要項

画像の代替テキスト

  • 写真：何が写っているかを具体的に書く。
    • △ 画像
    • ◎ 満開の桜並木の下を、傘を持った人たちが歩いている
  • 文字が入っている画像：その文字の内容も書く。
    • △ 秋の写真展の告知画像
    • ◎ 秋の写真展の告知画像。10月3日から10月20日、市民ギャラリー、入場無料
  • 図やグラフ：何を表していて、何が読み取れるかを書く。
    • △ 来場者数のグラフ
    • ◎ 月別の来場者数の棒グラフ。8月がもっとも多く、2月がもっとも少ない

体験と接点

設計できるのは接点だけ。接点の質を上げて、良い体験が生まれる確率を高めるところまでが仕事。

  • 体験とは、ユーザーがプロダクトに対して持つ期待・記憶・意味づけと、実際にプロダクトから受け取った刺激との相互作用で生まれる、極めて主観的な感情の総和。
  • 同じラーメンでも、行列に1時間並んで「絶対に美味いはずだ」と期待して食べるのと、ふらっと入って何の期待もなく食べるのとでは、まったく別の記憶として残る。ラーメン屋が設計できるのは、ラーメンそのものだけ。
  • デザイナーも同じで、どれだけ丁寧に画面を作っても、ユーザーが最後に何を感じるかは決められない。体験は、設計者の中ではなく、ユーザーの中で起きる出来事だから。
  • 接点とは、画面のレイアウト、情報の並び順、タップしたときの手応え、エラー時の言葉、空の画面に何を映すか、読み込みの速さ、通知の文面やタイミング。直接手を入れられるのはここだけ。
  • そこから先はユーザーのもの。最後に何を感じるかはユーザーに委ねるしかなく、それを自分の設計の手柄として抱え込まない。

出典：僕たちは「体験」なんて設計していない

「体験をデザインする」か「体験のためにデザインする」か

  • 派閥が分かれる。「デザイナーが体験をコントロールする」は強すぎる。
  • 設計とは本来、結果を保証する行為ではなく「望ましい状態を企図する」行為。結果の保証を求めると、建築も教育も、受け取られ方が環境次第の UI すら「設計不能」になる。
  • 主観的＝予測不能ではない。期待や意味づけは文化的にパターン化されているので、調査できるし設計の参照点になる。行列が生む期待だって店側が演出できる。それがデザイン。
  • 「接点の質を高めて良い体験の確率を上げる」は、UX 論が昔から言う design for experience の定義そのもの。
  • ある人の整理：「ユーザーに生じた体験」と「作り手の理想の体験像」を両方 UX と呼ぶのがズレの元。設計は担い手がコントロールできる範囲に使う言葉で、サービスは設計対象。一方、サービスを介してユーザーに生まれる体験はコントロール外なので設計対象ではない。良い体験の確率を上げる「追求」はできるが、100% 意図どおりは構造的にありえない。
  • 別の視点：デザインの概念を定義し直すより、デザインの対象がどう広がり、どんな知識や方法論（人類学・認知科学・経営学・情報科学・AI など）を取り込んで発展したかの歴史を時系列で書くほうが長く読まれる。いま再定義してもすぐ意味合いは変わるし、多義に多義を重ねて面倒になる。
AI でデザイン案を出すコツ

コツは大きく2つ。

  1. 試行回数を増やす：細かい作法にこだわらず、とにかく量を出す。
  2. 打率を上げる：良い案が出たら、その理由を AI に分析させて次のプロンプトに反映させる。指示が複雑になって伝わらなければ、自然言語でシンプルに伝え直す。スクリプトの形式にこだわるより、どの伝え方が要件の解像度を上げるかを見極めるほうが効く。

情報流通と風通し
  • 1on1 や times に閉じた話は、「相談だったのか」「アイデアだったのか」「意思決定だったのか」が分からない。組織として共有すべき問題が、その中に閉じ込められるリスクがある。
  • times は普段から読んでいる人しか情報を取れない。オープンに見えて、実はかなり人間関係に依存した情報流通。Slack に書いてあることと、必要な人に届くことは別。公開されていることと、共有されていることは違う。
  • よもやま依存の組織で一番怖いのは、「誰と仲がいいか」が情報格差になること。「風通しがいい」のではなく、情報流通が人間関係に依存しているだけかもしれない。
  • かといって「全部会議で話せ」「全部ドキュメントに残せ」にしたいわけではない。大切なのは、そこで生まれた情報のうち、組織に必要なものを正式な情報流通に戻すこと。
  • 次のような状態も風通しの良さ。コミュニケーションが多いことと、情報流通が健全であることは、似ているようで違う。
    • 特定の誰かと話さなくても、必要な情報にアクセスできる。
    • 参加していなかった意思決定でも、後から経緯を追える。
    • 人間関係ではなく、組織の仕組みとして情報が流れている。

デザインの考え方

デザインとアートの違い

美大生が作る UI は「独自の着飾った見た目」になりがちで、一枚絵としては綺麗でも通用しない。ソフトウェアの本質はパターン・複製・動的な挙動であって、渾身の一枚絵ではない。

出典：X のポスト

なんのためにデザインするのか

同じ題材でも、意図によってデザインは変わる。

  • どんな人に：年齢・性別、状況（受験生、新社会人）、ライフスタイル（食にこだわる、忙しい）、知識レベル、関心の高さ
  • 何を：作り方、バリエーション、おいしさ、美しさ
  • なぜ伝えたい：好きになってほしい、楽しんでもらいたい、理解してほしい、迷わせない、正確に伝えたい、覚えてもらいたい、商品を売りたい
  • いつどこで伝えるか：本、勝手に届く DM、学校や予備校の教科書、通勤途中で見る広告、本の冒頭か終わりか

初心者向け（「簡単でしょ」と思わせたい）デザインの注意：

  • 飾り付けや、動きのある文字・写真の配置にはしない。雑多に見えてしまう。
  • 説明しすぎる「親切」は、かえって情報量が多く小難しそうに見える。
  • やるべきは、シンプルな構成、大きい完成イメージ、ポイントだけ強調、癖のない書体、大きな文字サイズ。
スキューモーフィズムとニューモーフィズム

スキューモーフィズム

  • 語源は skeuos（容器・道具）＋ morphê（形状）。例：電卓アプリ。
  • デジタル UI を物理的なものに似せて、馴染みのない操作の学習コストを下げる手法。初見でも直感的に操作できる。
  • 光と影で立体感を出し、質感まで表現する。

ニューモーフィズム（流行らない理由）

  • New ＋ Skeuomorphism の造語。立体的なスキューモーフィズムと、フラット/マテリアルデザインを組み合わせた手法。明暗2色のドロップシャドウで、突き出て/くぼんで見せる。
  • ボタンを凹凸だけで表現するため、ON/OFF の差が分かりにくい。
  • コントラストが低く、状態を持たせづらいので、アクセシビリティが最悪。
  • ボタンでないものもボタンに見えてしまう致命的な欠陥があって廃れた。
  • デザインの自由度が下がり、強調したいところを強調しづらい。影もベースの色に依存して色味を足す必要がある。
  • おそらく外観以外の思想がない。触覚フィードバックがもっと入ってくれば、わんちゃんあるかも。
UI レビューのチェックリスト
  • 何が一番重要な情報か一目で分かるか
  • 余白に一貫性があるか
  • タップ領域は十分か
  • ボタンを押した結果が予測できるか
  • 戻り方が分かるか
  • 空状態を考慮したか
  • Loading 状態があるか
  • Error 状態があるか
  • 長い文字列でも崩れないか
  • アクセシビリティを確認したか

文言・問いかけ

  • 何を聞かれているかユーザーがわかるか
  • ユーザーにとって聞き馴染みのある言葉か
  • いつ何をしたらいいかわかるか
  • 問いとアクションが対応しているか
  • アクションがイメージしやすい工夫がされているか
  • 認識させたい順番を意識できているか
  • どれがメインかわかりやすいか
  • 書かなくても伝わることをわざわざ書いていないか
ダークパターン

やっていないか点検する。

  • Sneaking / Drip Pricing（隠れコスト）：頼んでいないオプションや手数料を、決済の途中でこっそり上乗せする。
  • Fake Urgency（偽の緊急性）：偽のカウントダウン。
  • Fake Scarcity / Fake Social Proof（偽の希少性・社会的証明）：「残り◯点」「◯人が閲覧中」「たった今売れました」で焦りや同調圧力をあおる。
  • Confirmshaming：辞退ボタンに「損する人生を選びます」などの文で罪悪感を刺激する。拒否リンクを薄く小さく隠すのも定番。
  • Misdirection / Interface Interference：押させたいボタンだけ巨大・派手にして、「閉じる」「解約」を極小・極薄にする。
  • Roach Motel / Hard to Cancel：加入は1秒、解約は引き止め・アンケート・電話のたらい回し。解約ボタンをわざと押せなさそうに見せる。
  • Preselection / Trick Wording：不要な有料オプションに最初からチェックを入れる。二重否定などのひっかけ文。
  • Nagging：通知許可・アプリ誘導・レビュー依頼を、断っても何度も出す。
  • Forced Continuity：無料トライアルから告知なしで自動的に有料課金する。
  • Privacy Zuckering：プライバシー設定をわざと分かりにくくして、個人情報を過剰に取る。
  • Disguised Ads：広告をコンテンツや「次へ」ボタンに偽装する。

意思決定とコミュニケーション

意思決定

  • やめるかどうか：理由が1つだけならやめない。2つ以上できたら検討する。
  • 人を頼るのは「まだギリギリになっていない段階」で。ギリギリで頼って断られ、罵倒されると、二重の極みのように心が壊れる。余裕があるうちなら、断られても耐えられる。

コミュニケーション

  • 情報は、他人を介すごとに落ちていく。
  • 社外・社内を問わず、10秒で説明できないものは聞いてもらえないし、前に進まない。説明が長いのは「こねくり回しすぎ」「考えきれていない不安が文字を増やしている」「完璧だけどズレている」のどれか。
  • アリストテレスいわく、ロゴス（論理）・エトス（信頼・人柄）・パトス（感情）がないと人は動かない。「君の主張にはロゴスしかない」と恩師に言われた話。
  • 外から見てすぐ思いつくアドバイスは、たいていすでに考え尽くされているか、いろいろな事情の結果。だから、背景を聞き出せない場面では偉そうなことを言わない。

会議で困ること

  • 目的が共有されないまま始まる。
  • 参加者の前提知識がそろっていないのに始まる。
  • 誰が決めるのか曖昧なまま議論が続く。
  • その場の思いつきで議題が増える。

「要はバランス」問題

  • 議論の途中の「要はバランス」は、多くの場合なにも言っていないに等しい。両サイドを冷笑して「まあ熱くならずに」と大人ぶるのは、中立ではなく濃いエゴ。意見を言えないことと中立は違う。
  • 対立＝悪ではない。速度・安全性・運用コスト・ユーザー影響…と論点の地図が増え、価値の軸が見えている状態は、議論が深まっている。「要はバランス」で止めると、生えかけた軸が折れて、大人っぽい空気だけが残る（議事録にも実装にも使えない）。
  • 止めるなら理由を持つ。「判断材料が足りない」「論点が3つに分かれたので分解したい」「人格評価に寄っているので案に戻したい」は貢献。「要はバランス」だけは、結論のふりをした停止命令。
  • 主張・反論・具体案を出す人は、みなリスクを負っている。なにも出さずに「要はバランス」は、手ぶらで鍋パに来て「味って大事だよね」と言うのと同じ。高級な無責任。

ヒアリング・インタビューで意識すること

  1. 指示語は具体名に置き換えて確認する：「あれ」「さっきの」→「A案のことですね？」。認識のずれを防げるし、オンラインの参加者もついていけるし、文字起こしや AI 分析の精度も上がる。
  2. 意見の「理由」まで掘る：「こういう人は使いそう」には「自分は使わないけど」が隠れがち（主語が他人にすり替わっている）。「あなた自身は使う？使わないならなぜ？」と主語を本人に引き戻す。
  3. 発言だけでなく「温度感」も解釈する：食い気味の「めっちゃ欲しい！」と「う〜ん、まぁ使うと思います」は別物。話し方の勢いや表情で熱量の差をとらえる。
人とマネジメント
  • 若い人はライフイベントを経験していないことが多く、他人のキャリアや人生を背負う経験・コンピテンシー・共感力がまだない。なので、マネジメントは十分にできていないことが多い。
  • 会議中は無言なのに、会議のあとで Teams や Slack に「念のため補足ですが」と書かない。
  • べらべら流暢に喋る人が、頭が良くて有能とは限らない。「流暢に喋る能力」に長けているだけ。それに惑わされるのは、見る目がない証拠。
  • 「許可を求めるな、謝罪せよ」は超訳。原文は "It is easier to ask forgiveness than it is to get permission"。「事前に許可を得るより、あとで許してもらうほうが楽」と訳すのが正確。
  • トヨタ式のなぜなぜ分析は「人」に使うものではない（人は不規則性が高くて答えにたどり着けない）。本来は道具・環境・マニュアルに対して使う品質改善の手法。人を変えても、環境や前提条件を変えなければ、別の人が同じ失敗をする。
  • マネージャーにとっての「いい話ができた30分」が、部下にとっては「上司の自己確認に付き合わされた30分」として記憶されている。
  • すでに「見下す枠」に入れられた人は、なにをしても粗探しされる。
  • 「教える」ことに強く惹かれる人の支配欲を疑う。子どもは怒鳴っても「はい！」と従い、数十人が真剣に話を聞く。支配欲に飢えた人には気持ち良すぎる状況で、そうでない人でも狂いうる。しかも支配を「愛がある」と言い訳する指導者もいるのでタチが悪い。
  • 部下・後輩への接し方の線引き：ちゃん・くん付けしない、お友達感覚にならない、愚痴に迎合しない。
  • 良いマネージャーの見分け方（顧客の追加要望への対応）：「YESマン」か「スコープ外なので」でリソースの議論をしてしまう人は痛い目に遭う。「B をするなら A は落とすことになります」と優先順位の議論ができる人が得をする。顧客とメンバーの両方を守れる人が良いマネージャー。「スコープ外」で突っぱねるのは正しいかもしれないが、信頼だけが減る。
  • マイナス評価は人が辞めるだけ。「頑張ったけど未達だから減給、悔しさをバネに」で発奮する人は0人。具体的な改善点とセットでないと機能しない（下手すると「もう辞めていい」というメッセージになる）。
  • 海外の人との交渉が難航したら、日本語でブチ切れる。
  • 50歳以上にはメールせずに電話する。
AI っぽい文章

特徴（避けたい）

  • タイトルに、謎の英語や日本語の説明文を変なところに付けがち。
  • シンプルな動詞・形容詞を見出しに使いがち（英語の直訳感）。
  • 単語が全部薄味（ローコンテキスト）。
  • 具体を列挙して抽象化し、結論を後半に持ってくる流れ。
  • 「効く」（AI 文章疑いワード、個人的ランキング第1位）。

読みづらい理由（仮説）

5W1H を全部、頭から順に書いてしまうから。書く側は「過不足なく書かれているからいいか」と思うが、読む側は「HOW だけ知りたい」「WHY だけ知りたい」ことがよくある。そのニーズに応えられないと、その文章は読まれなくなる。

プログラマの誓い

Robert C. Martin（Uncle Bob）による、開発者としての職業倫理（The Programmer's Oath）。

  • 害を及ぼすようなコードは書かない。
  • 自分が書くコードが最善であることを誓う。振る舞いや構造が悪いコードをリリースしない。
  • リリースごとに、コードが意図どおり動くことの「速く・確実で・再現可能な証明」もあわせて作る。
  • ほかの人の進みを妨げないよう、こまめに小さくリリースする。
  • あらゆる機会に、ためらわずコードを改善する。決してコードを悪くしない。
  • 自分と他人の生産性を最も高く保つ。生産性を下げることはしない。
  • ほかの人が自分をカバーでき、自分もほかの人をカバーできる状態を保ち続ける。
  • 規模と正確性において正直な見積もりを出す。確信のない約束はしない。
  • 常に学び、自分の技術を磨き続ける。
ビジネスの観察

サイゼリヤの閉店（家賃2倍の値上げ交渉で撤退）

  • 地価高騰で家賃が上がり、「社会的インフラ」になった店でも撤退する時代。個人店にも波及する。
  • 全経費が上がっている飲食で、デフレ価格が忘れられない客ばかり集めてもくたびれ損。安さで集めた客層は、コストが上がる局面で足かせになる。

メガベンチャーが儲かる理由

  • メガベンチャーが儲かっているのは、技術力が高いからではなく、営業とマーケティングが上手いから。その余裕で技術に投資できているだけ。
  • なので「うちは技術力が高いから他所とは違う」とイキるエンジニア社長や CTO のスタートアップは、やめておく。

プロダクトは目的ではなく手段

企業はアプリを作ること自体を目的にしていない。ある経済活動を達成するためにアプリが必要だから作っているだけ。アプリは、目的を達成するための100個の手段のうちのひとつ。

大企業の新規事業の難しさ

DeNA は新規サービスに広告を打ちまくっているのに、全然売れていなさそう。大きい会社で新規事業をやると、当事者意識や「お金が溶ける感覚」を持ってもらうのがかなり難しいのかも。

商社はなにをしているのか

  • 「口座を持っていない中小と大手の間に入って、お金をもらうだけ？楽すぎない？」という疑問への答え：信用供与（与信）が本業。
  • 例：中国のバッテリーメーカーにツテがあるブローカーのおっちゃんは、商材の目利きはできるが資金がない。商社が100億円相当の取引に信用供与したので、無事100億円分のバッテリーを客に売れた。
  • 商社は間に入ることで、取引のリスク（代金回収・履行）を引き受けている。責任を取るのが仕事。
  • 日々していることは、連絡、進捗確認、巻き取り依頼。

フォーブス「Under 30」はペイド

「フォーブスに載りました！」で、テレビ局の考査が NG になった人もいた。特に Under 30 はペイドなので、実績としてアピールするときは注意。

良いマーケターは良い消費者

  • 「安い店で高いお金を使う」は悪手。自分の欲を磨いてお金を使う。実力のあるマーケターほど、ブランド品・良い家・旅行にお金を使う。消費者になる体験を増やすと「欲しい側」の解像度が上がり、実際に CPA を下げられて、事業アイデアも湧く、という証言。
  • 欲を磨く＝浪費の肯定ではなく、ユーザーがお金を払う瞬間の解像度を上げること。自分がなにに価値を感じて財布を開くかの感度を鈍らせない。
  • たくさんお金を使う人ほど「客はどの瞬間にお金を使いたがるか」が手に取るように分かる。逆に、節約上手で支出に抵抗がある人は、価格設定が低すぎがち。
  • スモールビジネス界隈の「禁欲してランニングコストを下げろ」は、打席に立てる寿命を延ばす意味では正しい。ただ、それとは別の軸の話。
  • 海外マーケの落とし穴：日本の IP から英語で TikTok マーケをしても、東南アジアにしか届かない。しかも東南アジアはプリペイドカード文化なので、決済の引き落としエラーが多発してつらい。ターゲット地域と決済インフラをセットで見る。
世の中の観察
  • 「見て見ぬふりをすることが最適解」だった時代が長すぎたと思う。
  • 中道・共産などを支持する人への（個人的な）印象：現実感がなく、性善説ベースの理想論・綺麗事ばかり。なのに他人に対しては悪口ばかり言っている。
  • 北海道はどこもインバウンド地獄。地元のタクシー運転手が「もう北海道は諦めて東南アジアの物件を買った」と言っていた。地元民でさえ東南アジア移住を考えるほど。
  • 同性カップルの住宅ローン（ペアローン）の審査は、観測範囲では今のところ全員「埼玉りそな銀行」が通してくれている。
  • プロフィールに「AI」と「開発」が両方入っている人を、無意識にうっすら避けるようになっている（最近始めた人は長く続かなそう、AI で暴れすぎ、という偏見）。そういう人に「これどうやってるんですか？」と聞かれてもスルーしがち（AI で雑にパクられるから）。AI 時代に生まれた新しい警戒感。
  • 日本人は海外で徒党を組むのが苦手で、海外で事業を興しても個人戦になりがち。なりふり構わず徒党を組んで同胞の利益を最大化する印僑・華僑とは対照的。
  • 海外では日本人を頼らないのが正解になりがち。日本人というだけで近づくと、足元をすくわれることもある。
  • シリコンバレーの日本人起業コミュニティは「資金調達＝成功」の考え方が根にあるので、染まると危険。
